# Decision log

| ID | Decision | Status |
|---|---|---|
| DD-001 | GDD defines design; Content Studio executes it as structured content. | Approved |
| DD-002 | Concrete Dungeon Levels and Stages exist in Content Studio, not Markdown. | Approved |
| DD-003 | The published release manifest is the immutable runtime content snapshot. | Approved |
| DD-004 | Compatible humanoids share a Rig Profile contract, not necessarily one body mesh. | Approved |
| DD-005 | Tactical Pause unlocks when DL 2 becomes active. | Approved design rule; release action set pending |
| DD-006 | Persistent database schema changes use forward-only numbered migrations. Runtime startup must not drop or recreate permanent tables. | Approved |
| DD-007 | Ordinary Equipment is Account-bound and held in the Account Layer's Account Inventory. One Equipment instance can never be used twice: it is either unassigned or occupies exactly one Equipment Slot in one Hero's Equipment Configuration, and cannot appear in both the Primary and Secondary Weapon Configuration. Each Equipment item contains its own usage rules, such as required Hero Level, rather than deriving them from Item Level. A Hero may equip an item only when it meets all of the item's usage rules, so a Hero below an item's required Hero Level cannot equip it. Moving an assigned item to another eligible Hero requires Transfer and Unequip. Usage rules are checked when an item is assigned; if a content release later changes them, an existing assignment stays on its Hero. Hero-bound Equipment is an explicit exception. | Approved |
| DD-008 | Content Studio includes a customer-service page that can look up any content and player data, and apply approved corrections to player data. It requires a separate support role, distinct from content authoring. Lookups and corrections go through the owning services' protected APIs, never directly to a database, and every lookup and correction is audited. | Approved |
| DD-009 | Content Studio is a cloud-hosted application on the Cloudflare platform defined in the service architecture. The POC Content Studio was a test: its application stack, framework, ORM, repository layout, schema, and migrations are not a baseline and are re-evaluated before the first Content Studio Feature Request. | Approved |
| DD-010 | Cloudflare is the cloud platform for Dungeon Destiny's services. The one exception is the Godot dedicated game server: it is packaged as a host-independent container image and is initially hosted on the owner's AWS server. The game-server host may change later without changing the container or its contracts with the Worker. | Approved |
| DD-011 | The game targets Android and iOS at launch. Players sign in with Google or Apple; no passwords are stored. Player Identity is built inside the Cloudflare Worker: it verifies the Google or Apple sign-in, maps it to an Account in Player D1, and issues a short-lived signed access token checked by the API Gateway and a revocable refresh token stored in Player D1. One Account may be used on several devices, but only one at a time: starting an active game session ends the previous device's session. | Approved |
| DD-012 | Every gameplay run, solo and co-op, executes on the authoritative Godot dedicated server. Where a run executes is a per-game-mode policy chosen by the Session Orchestrator, so solo runs may later move to the client without a rewrite. To keep that possible, the server and client builds share one Godot simulation code base, every run ends with a result sent through the same Results and Progression contract, and solo play does not depend on server-only features. Server-side changes must not require a client app-store update: game-server builds, server-executed rules, server hosts and addresses, and published content are deployed independently. Clients find game servers only through the Session Orchestrator and connect to them through one stable Cloudflare-proxied endpoint; Cloudflare Load Balancing health-checks the game servers and routes each session to the server named in its signed connection ticket, so servers can be added, moved, or replaced behind it. The realtime protocol is versioned and stays backward compatible with every supported client version, and the client renders authoritative state and published content instead of embedding rules the server may change. A client update is required only for new client features or when a client falls below the minimum supported version. | Approved |
| DD-013 | The realtime transport between the Godot client and the Godot dedicated game server is WebSocket over TLS, carried through the Cloudflare-proxied endpoint defined in DD-012. The Godot client and server keep the transport behind one network layer, so a later change to UDP or WebRTC does not affect gameplay code. Early tests on real mobile networks must confirm acceptable latency. | Approved |
| DD-014 | Game-server crash recovery is required from the initial version for solo and co-op runs. After a game-server crash, the run resumes from its latest durable checkpoint stored outside the game server. A small amount of progress since that checkpoint may be lost. Permanent player data remains safe, and rewards cannot be granted twice. The checkpoint interval, checkpoint contents, storage, and recovery ownership remain to be decided. | Approved |
| DD-015 | The Cloudflare Worker backend is written in TypeScript, starting with the development Worker named `dd-dev`. TypeScript is compiled to JavaScript for execution on Cloudflare. | Approved |
| DD-016 | Cloudflare infrastructure is managed with Terraform, and Worker code is deployed with Wrangler. Terraform state is kept in a Cloudflare R2 bucket, never in the repository. Terraform code lives in `infra/terraform/`, with one folder and one state per environment under `infra/terraform/envs/`, starting with `dev`. | Approved |
