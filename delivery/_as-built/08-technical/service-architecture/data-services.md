# Data services

This page describes the databases that have been built for Dungeon Destiny,
their tables, how their structure is changed, and how they are read.

Sources: [FR-00004: Content D1 and user model](../../../FR/FR-00004-content-d1-user-model/README.md).

## Content D1

Content D1 holds Content Studio's users, roles, permissions, and audit
records. It holds no player data.

| Item | Value |
|---|---|
| Database | `dd-dev-content`, a Cloudflare D1 database |
| Terraform resource | `cloudflare_d1_database.content` in `studio.tf`, with `jurisdiction = "eu"` and read replication disabled |
| Owner | `studio-api`, bound as `CONTENT_D1`; no other Worker binds it |
| Database ID | Set in `apps/studio-api/wrangler.jsonc` from the Terraform output `content_d1_id`; it is not a secret |
| Schema | `apps/studio-api/src/db/schema.ts`, in Drizzle ORM `0.45.4` |
| Migrations | `apps/studio-api/migrations/`, generated by drizzle-kit `0.31.11` and applied by Wrangler |

IDs are text UUIDs from `crypto.randomUUID()`, and times are ISO 8601 UTC
text. Email addresses are stored in lower case.

## Tables

| Table | Columns |
|---|---|
| `users` | `id`, `email` (unique), `display_name`, `status` (`active` or `deactivated`, default `active`), `created_at`, `updated_at` |
| `roles` | `id`, `name` (unique), `description`, `created_at`, `updated_at` |
| `permissions` | `name` (primary key, such as `users.manage`), `area`, `description`, `purpose`, `added_by` (the Feature Request) |
| `role_permissions` | `role_id`, `permission_name`; primary key on both; deleting a role deletes its rows |
| `user_roles` | `user_id`, `role_id`; primary key on both, and an index on `role_id` |
| `audit_events` | `id`, `occurred_at`, `actor_email`, `action`, `target_type`, `target_id`, `before`, `after` (JSON text), `request_id`; an index on `target_type` and `target_id` |

Users are deactivated, never deleted. The permissions are defined in code in
`packages/contracts/` and copied into the `permissions` table by a migration
for each Feature Request that adds them. The role and permission model is
described in [Access and edge services](access-and-edge.md).

`studio-api` writes each change and its audit record in one D1 batch, so a
change is never stored without its audit record. Every query uses bound
parameters.

## Migrations

| Migration | Contents |
|---|---|
| `0000_user_model.sql` | The six tables and their indexes |
| `0001_permissions_fr_00004.sql` | The four FR-00004 permissions |

drizzle-kit generates the next numbered migration from the schema, and
Wrangler applies it, first to the local database used by the tests and by
`wrangler dev`, then to `dd-dev-content` in Cloudflare. A migration is applied
to Cloudflare before the `studio-api` code that needs it is deployed. Applying
a migration to Cloudflare changes the live database and needs the project
owner's approval; listing the migrations changes nothing. A migration that
has been applied to Cloudflare is never edited. The commands are in
`AGENTS.md`, and the rules in `doc/08-technical/database-change-management.md`.

## Reading Content D1

`devops/db/query.sh` reads Content D1 and never writes. It runs a named query
or, with `sql`, one `SELECT` statement:

| Query | Result |
|---|---|
| `tables` | The tables in the database |
| `users` | Users with their status and roles, without email addresses |
| `roles` | Roles with their number of users and permissions |
| `permissions` | Permissions with their area and the Feature Request that added them |
| `audit` | The 20 latest audit records, without email addresses |
| `migrations` | The migrations not yet applied |
| `sql "<SELECT ...>"` | One `SELECT` statement; any other statement, more than one, or an empty one is refused |

The script reads `dd-dev-content` in Cloudflare by default and refuses when
the credentials are not loaded; with `--local` it reads the local database and
needs no credentials. It uses the workspace's own Wrangler, so it works when
pnpm is not on the `PATH`. Running it needs no approval. The named queries
leave out email addresses, because their output is often shared. The
Content D1 how-to is `doc/howto-content-d1.md`.

## Verification

FR-00004, accepted on 2026-10-14. The tests in the Workers runtime apply the
migrations to an empty local database and check that every table is created
and that the `permissions` table matches the permission list in code. The 18
tests in `tests/FR-00004/db_query_test.sh` were written before the script and
failed first; they now pass, covering each named query, `sql` with one
`SELECT` and the statements it refuses, Cloudflare by default, `--local`, the
refusal without credentials, and that no named query selects an email
address. Against Cloudflare, no migrations are waiting for `dd-dev-content`,
and its `permissions` table holds the four FR-00004 permissions.
